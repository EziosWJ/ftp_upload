问题

AppConfig 把设备配置、元数据、调度、FTP 全部塞在一个类里。每次 API 调用都加载整个配置文件，即使只修改一个字段。

方案

拆分为 4 个独立的配置存储模块，各自管理自己的 JSON 文件或独立的配置区域。

收益

  • locality: 每个关注点独立
  • leverage: 接口缩小
  • 消除全量读写开销

问题

~40 个端点全部直接操作 config 对象，basic-devices / safety-certs / measure-points / realtime 四组 CRUD 代码几乎完全相同（~80% 重复）。

方案

引入通用 CRUD 服务工厂或基类，API 层只做参数解析和响应格式化。

收益

  • leverage: 一个服务接口覆盖 N 个端点
  • locality: 业务逻辑集中
  • 删除 ~300 行重复代码

3. 加深 config.py — 去除浅封装，添加缓存

Worth exploring in-process
app/config.py

Before — 浅模块

# 接口 ≈ 实现 (shallow)
load_config() → 读文件 + parse
save_config() → dump + 写文件
get_config() → load_config() 的别名
update_config() → save_config() 的别名
# 无缓存，每次读磁盘
# scheduler 每次轮询都调用

After — 深模块

# 接口小，行为多 (deep)
get_devices() → 缓存 + 返回
update_device() → 验证 + 原子写
# 内部: 缓存 + 文件锁
# 调用者无需知道存储细节

问题

get_config() 和 update_config() 是零价值别名。无缓存导致 scheduler 每次轮询都读磁盘。CONFIG_FILE 路径硬编码，测试不友好。

方案

删除别名函数，添加内存缓存（带 TTL 或文件 mtime 检查），支持路径注入。

收益

  • 接口缩小 50%
  • 消除每次轮询的文件 I/O
  • 可测试性提升

收益

  • leverage: 一个接口管理所有后台任务
  • locality: 生命周期逻辑集中
  • 可测试性: 无全局状态泄漏

5. 修复 test_device 对 collector seam 的破坏

Worth exploring local-substitutable
app/web/api.py · app/collectors/

Before — Seam 被绕过

flowchart LR
    API["api.py: test_device"]
    API -->|"直接 import"| MC["ModbusCollector"]
    API -->|"直接 import"| SC["S7Collector"]
    BC["BaseCollector"] -.->|"被忽略"| API

    style API fill:#fef3c7,stroke:#fbbf24,color:#92400e
    style MC fill:#fee2e2,stroke:#f87171,color:#991b1b
    style SC fill:#fee2e2,stroke:#f87171,color:#991b1b

After — 通过 Seam 调用

flowchart LR
    API["api.py: test_device"]
    API -->|"通过工厂"| Factory["CollectorFactory"]
    Factory -->|"返回"| BC["BaseCollector"]
    BC --> MC["ModbusCollector"]
    BC --> SC["S7Collector"]

    style BC fill:#1e293b,stroke:#1e293b,color:#fff
    style Factory fill:#e0e7ff,stroke:#818cf8,color:#3730a3

问题

api.py 直接 import ModbusCollector 和 S7Collector，绕过 BaseCollector 抽象。添加新协议必须修改 api.py。

方案

引入 CollectorFactory，api.py 只依赖 BaseCollector 接口。工厂根据 device_type 返回正确的采集器。

收益

  • Seam 真正可替换
  • 新协议无需改 api.py
  • 测试可用 mock 采集器

🏆 首选建议

候选 #2: 引入服务层消除 API 重复 — 这是投入产出比最高的改动。 ~40 个端点中 80% 是相同的 load → mutate → save 模式，basic-devices / safety-certs / measure-points / realtime 四组 CRUD 几乎完全相同。 引入一个通用 CRUD 服务工厂可以消除 ~300 行重复代码，同时为后续拆解 AppConfig（候选 #1）打下基础。 改动范围集中在 app/web/api.py 和新建的 app/services.py，风险最低。
